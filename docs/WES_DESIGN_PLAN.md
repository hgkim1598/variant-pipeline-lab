# 1. 전제 — 확정된 사실

> **이 장은 협상 대상이 아닙니다.** 화면은 여기 적힌 범위 안에서만 설계합니다.
> 이 장의 모든 항목은 `[코드근거]`입니다. 저장소를 읽기 전용으로 전수 조사해 확인한 사실입니다.

## 1-1. 이 서비스가 하는 일

Illumina paired-end WES FASTQ 한 쌍을 올리면 `script/main.sh`(11단계, 5,207줄)가 실행되어 **raw VCF까지** 만듭니다.

핵심 완료 지점은 `<샘플>.raw.vcf.gz` 이고, **필터링·주석·ACMG 분류는 전부 선택 단계이며 기본값이 꺼져 있습니다.**

> **근거** `[코드근거]` — `main.sh`의 `core_summary.json` 생성부가 `core_endpoint`를 `"raw VCF (no filtering applied)"`로 기록합니다. `config_builder.py`는 `optional_steps.filtering`과 `.annotation`을 **항상 `false`로 고정**해서 넘깁니다. 즉 웹에서 제출하는 한 필터링·주석은 실행되지 않습니다.

## 1-3. 화면 설계를 직접 제약하는 사실 14가지

| # | 사실 | 화면에 미치는 영향 |
|---|---|---|
| F1 | 샘플은 1회 1개만. 2개 이상 `400` | "여러 샘플 동시" 표현 전면 제거. **여러 lane은 허용** |
| F2 | `.fastq.gz` / `.fq.gz`만 허용 | accept 목록에서 비압축 확장자 제거 |
| F3 | `WES_RUN_MODE` 기본값 = `check_only` | 기본 상태에서 **분석 산출물이 안 나옵니다.** `precheck` / `full`을 별개 화면으로 |
| F4 | worker 스레드 1개, 순차 실행 | `queued`는 "곧 시작"이 아님. **대기열 순번·앞선 run 정보는 API가 없습니다** |
| F5 | SSE 없음. 3초 폴링만 | "실시간 연결" 표기 금지 |
| F6 | 로그는 `pipeline.log` **마지막 200줄**뿐 | 전체 로그 다운로드 액션을 만들지 않습니다 |
| F7 | `progress` = 완료단계수 ÷ 계획단계수 | **"6/8단계"를 1차, %를 2차** |
| F8 | `unsupportedOptions` 존재. 옵션 9개 중 실제 전달은 3개 | 새 화면에서 6개 제거. **과거 Run 상세에는 기록 표시 필수** |
| F9 | `availableViews`는 최대 `["coverage-summary"]` 1종 | 프론트가 정의했던 결과 뷰 7종 중 6종은 데이터가 없습니다 |
| F10 | `GET /api/jobs` (목록) 없음 | 실행 목록은 **브라우저 로컬 저장 기반**으로만 가능 |
| F11 | `profileId`는 이미 `GET /api/jobs/{id}` 응답에 있음 | navigation state 의존을 없앨 수 있습니다 |
| F12 | 인증 전혀 없음 (localhost 전용) | 로그인·계정·공유 UI 없음 |
| F13 | **full WES 실행이 아직 검증되지 않음.** 실행 기록 6건 전부 check-only, 전부 실패 | full 결과 화면의 모든 수치는 mock (1-6) |
| F14 | 브라우저는 새로고침 후 로컬 `File` 객체를 되찾을 수 없음 | 이어받기는 **"같은 파일 재선택"** 전제로만 |

> **근거 (F1)** `[코드근거]` — `jobs.py`의 검증 2번: `"this build accepts one sample per submission…"`. 백엔드 주석에 "multi-run fan-out is not implemented yet"이라 명시되어 있습니다.
>
> **근거 (F3)** `[코드근거]` — `config.py`에서 `WES_RUN_MODE`의 기본값이 `"check_only"`입니다. `check_only`면 `plannedSteps`가 `["00_input_validation"]` 1개뿐이고, `--check-only` 플래그가 붙어 실행됩니다. **이 사실이 결과 화면 설계를 둘로 쪼갠 이유입니다.**
>
> **근거 (F4)** `[코드근거]` — `worker.py`가 `threading.Thread` 1개로 `queue.Queue`를 소비합니다. Celery도 Redis도 없습니다. `requirements.txt` 주석에 "No SQLAlchemy, Celery, Redis or driver"라고 직접 적혀 있습니다.
>
> **근거 (F7)** `[코드근거]` — `run_status_reader.py`가 `round(완료단계수 / 계획단계수 × 100)`으로 매 요청마다 계산합니다. `main.sh` 자체에는 `progress` 필드가 없다고 주석에 명시되어 있습니다. **즉 "63%"는 남은 시간과 아무 상관이 없습니다.** 정렬 단계 하나가 90분인데 8단계 중 하나이므로 12.5%로 계산됩니다.
>
> **근거 (F13)** `[코드근거]` — `runs/` 아래 실행 디렉터리 6개를 확인한 결과 전부 `check_only`이고, 도구·참조유전체 부재로 `00_input_validation`에서 실패했습니다. **full 실행 산출물 목록은 코드에서 읽은 것이지 실측이 아닙니다.**
>
> **근거 (F14)** `[표준]` — HTML File API의 `File` 객체는 사용자의 명시적 선택(`<input type=file>` 또는 drop)으로만 생성됩니다. 페이지 리로드 시 JavaScript 힙이 소멸하므로 참조가 사라집니다. File System Access API의 핸들 영속화는 Chromium 계열 일부에서만 지원되고 사용자 권한 재확인이 필요해, 크로스 브라우저 기능으로 전제할 수 없습니다.

## 1-4. 파이프라인 단계

| 순서 | step_id | 구분 | 화면 표시명 | 부제 |
|---|---|---|---|---|
| 1 | `00_input_validation` | core | 입력 검증 | 파일·참조 데이터 점검 |
| 2 | `01_raw_qc` | core | 원본 품질 검사 | FastQC |
| 3 | `02_preprocessing` | core | 전처리 | fastp (현재 설정은 건너뜀) |
| 4 | `03_alignment` | core | 참조 유전체 정렬 | BWA-MEM |
| 5 | `04_processing` | core | BAM 정리·보정 | MarkDuplicates + BQSR |
| 6 | `05_coverage_qc` | core | 커버리지 검사 | mosdepth |
| 7 | `06_variant_calling` | core | 변이 검출 | GATK HaplotypeCaller |
| — | `08_filtering` | optional | 변이 필터링 | bcftools |
| — | `10_annotation` | optional | 변이 주석 | bcftools + ClinVar |
| — | `11_intervar` | optional | ACMG 자동 분류 | InterVar |
| 8/9 | `99_finalization` | core | 결과 정리 | 요약·방법·산출물 목록 |

> **근거 (도구명을 부제로 내린 이유)** `[제품관찰]` + `[설계판단]` — wet-lab 배경 사용자는 `BWA-MEM`이라는 문자열보다 "지금 read를 참조 유전체에 배치하는 중"이라는 의미를 먼저 필요로 합니다. 반대로 바이오인포매틱스 사용자는 도구명이 있어야 신뢰합니다.
> **둘 중 하나를 고르지 않고 위계를 줬습니다** — 1차 라벨은 의미, 2차는 도구명. 이렇게 하면 두 사용자 모두 자기가 찾는 정보를 먼저 봅니다.
>
> **근거 (07·09가 없는 것)** `[코드근거]` — `main.sh`의 `STEP_KIND` 배열에 07과 09가 존재하지 않습니다. 번호가 비어 있다는 건 **나중에 채워질 자리가 설계상 열려 있다는 뜻**으로 읽었고, 이것이 4-2 Step Registry의 직접적 근거가 되었습니다.

## 1-5. 상태 값 전수

| 종류 | 값 |
|---|---|
| Job (6) | `queued` `running` `completed` `completed_with_warnings` `failed` `cancelled` |
| Step (6) | `pending` `running` `completed` `warning` `failed` `skipped` |
| 검증 항목 (3) | `PASS` `WARN` `FAIL` |
| 결과 타입 (2) | `precheck` `full` |
| Optional 단계 (6) | `not_run` `unsupported` `failed` `completed` `file_missing` `unavailable` |

> **근거** `[코드근거]` — `schemas.py`의 `Literal` 타입 정의에서 전수 추출했습니다.
>
> **이 표가 왜 중요한가** `[설계판단]` — 상태 값을 전수 확보하지 않으면 **디자이너가 "정상 3개"만 그리고 끝냅니다.** 실제로 기존 화면은 `completed_with_warnings`와 `skipped`를 제대로 구분하지 않았습니다. 상태 목록을 먼저 확정하고 화면을 그리면, 색·아이콘·문구를 6종 전부 정의하게 되어 자연스럽게 빈틈이 줄어듭니다.

## 1-6. mock 값 표기 규칙

> ⚠️ **이 문서의 `92.4×`, `34,821`, `99.42%`, `38분 12초` 등 모든 수치는 레이아웃 검토를 위한 합성값이며, 실제 WES 실행 결과가 아닙니다.**

**적용 규칙 3가지**

1. 와이어프레임에서 mock 수치가 있는 블록에 `⟦mock⟧` 표시
2. 코드에서 예시 데이터는 **`src/mocks/fixtures/` 밖으로 나가지 않습니다.** 컴포넌트나 JSX에 숫자를 직접 쓰지 않습니다
3. AI에게 화면을 시킬 때 이 규칙을 매번 명시합니다

> **근거** `[코드근거]` + `[설계판단]` — F13 때문입니다. full 실행이 검증되지 않았는데 와이어프레임에 구체적 숫자가 있으면, **코드 생성 단계에서 그 숫자가 fixture가 아니라 컴포넌트에 박힐 위험**이 실재합니다. 실제로 v1 문서에는 이 규칙이 없었고, GPT 검토에서 이 위험을 지적받아 v2에 추가했습니다.
>
> 부수 효과가 하나 더 있습니다. fixture로 격리하면 **`job.running` / `job.failed` / `results.precheck` / `results.full` 같은 상태별 fixture를 만들게 되고**, 그러면 13-1의 "4가지 상태 전부 설계" 요구가 자연스럽게 강제됩니다.

## P0. 확장 가능한 Run Workspace로 설계한다

> 현재 존재하지 않는 모듈은 화면에 미리 표시하지 않지만, **들어갈 자리는 구조적으로 열어 둡니다.**

> **근거** `[코드근거]` + `[설계판단]`
>

> 1. `main.sh`의 단계 번호에 07·09가 비어 있습니다 → 단계는 늘어날 예정입니다
> 2. `optionalSteps`의 상태 어휘 6개 중 `unsupported`·`unavailable`은 현재 코드가 방출하지 않습니다 → 백엔드도 확장을 예상하고 있습니다

## P1. 실행(Run)은 페이지가 아니라 객체다

> **근거** `[제품관찰]` + `[코드근거]`
>
> Seqera Platform · DNAnexus · Seven Bridges · Terra가 공통으로 쓰는 구조입니다. 네 제품 모두 **실행 목록 → 실행 상세** 계층을 가지고, 실행 상세 안에서 tasks / inputs / outputs / logs로 내려갑니다. 일회성 페이지가 아니라 다시 돌아와 조회하는 객체로 취급합니다.
> 참고: Seqera Platform 모니터링 문서, DNAnexus "Monitoring Executions" 문서 (21장)

## P2. 시스템이 아니라 사람의 언어로 쓴다

> **근거** `[표준]` — Nielsen 휴리스틱 #2 "Match between system and the real world": 시스템은 사용자에게 익숙한 단어와 개념으로 말해야 하며, 시스템 내부 용어를 쓰지 않아야 합니다.
> 참고: Nielsen, "10 Usability Heuristics for User Interface Design" (NN/g, 1994·개정)
>
> `[코드근거]` 현재 화면은 `Job ID: wes-20260828-143201-8eccbb`를 제목 바로 아래 배치합니다. 사용자가 이 실행을 식별하는 단서는 **샘플명과 분석 종류**이지 hex 문자열이 아닙니다.
>
> `[설계판단]` Run ID를 없애지는 않았습니다. 서버 로그와 대조할 때 반드시 필요하기 때문입니다. **제목에서 메타 영역으로 내리고 복사 버튼을 붙였습니다** — 필요한 사람은 여전히 쓸 수 있고, 아닌 사람의 눈에는 덜 띕니다.

## P3. 진행 상태는 %가 아니라 단계로 말한다

> **근거** `[표준]` — NN/g의 긴 대기 시간 연구는, 정확한 ETA를 산출할 수 없을 때 **완료 단계와 남은 단계 목록을 보여주는 것이 임의의 퍼센트보다 낫다**고 권고합니다. 또한 10초를 넘는 작업에는 percent complete, elapsed time, 현재 단계를 제공하도록 합니다.
> 참고: NN/g "Designing for Long Waits and Interruptions", "Response Times: The 3 Important Limits" (21장)
>
> `[코드근거]` **이 프로젝트에서는 근거가 더 강합니다.** F7에서 확인했듯 `progress`는 완료 단계 비율이지 시간 비율이 아닙니다. 정렬 90분과 결과 정리 8초가 **똑같이 1/8로 계산됩니다.** 즉 "50%"는 "절반 남았다"를 전혀 뜻하지 않습니다.
>
> `[설계판단]` 진행률 바를 없애지는 않았습니다. 대신 **1차 정보를 `변이 검출 · 6/8단계 · 1시간 18분 경과`로 바꾸고, 바는 보조로 내렸습니다.** 가짜 ETA는 만들지 않습니다 — 계산 근거가 없는 숫자를 보여주는 것이 아무것도 안 보여주는 것보다 나쁩니다.

## P4. 없는 기능은 예쁘게 만들지 말고 없앤다

> **근거** `[설계판단]` — 이 원칙은 GPT 검토에서 제안받아 v2에 추가했습니다. 다만 **적용에 조건을 달았습니다.**

> "false면 이상 상태이니 경고로 노출하라"는 일반 원칙은 맞지만, **"무엇이 이상인가"가 문맥에 따라 다릅니다.** `manifestConsistent: false`는 full 실행에서 구조적으로 항상 발생하는 정상값이라, 경고로 올리면 모든 정상 실행에서 경고가 뜹니다. 상세는 13-4에 정리했습니다.

> 이 사례가 **면접에서 쓰기 좋습니다** — 좋은 원칙을 받아들이되 코드 사실과 대조해 적용 범위를 조정한 사례입니다.

## 4-2. Step Registry

```ts
type StepMeta = {
  id: string;             // "03_alignment"
  label: string;          // "참조 유전체 정렬"
  subtitle?: string;      // "BWA-MEM"
  description?: string;
  kind: 'core' | 'optional';
  metricLabels?: Record<string, { label: string; unit?: string; format?: 'int'|'pct'|'float' }>;
};
```

**렌더 규칙**
```
plannedSteps 순회
  → registry에 있으면  label / subtitle / description 사용
  → registry에 없으면  step_id 원문을 label로 사용, kind는 'core'로 가정
                       (경고나 오류를 내지 않고 그대로 표시)
```

> **근거** `[코드근거]` + `[설계판단]`
>
> 기존 코드에도 `STEP_LABELS` 사전이 있고, 사전에 없는 `stepId`는 원문 그대로 표시하는 fallback이 이미 있었습니다. **좋은 판단이었고, 그대로 계승했습니다.**
>
> 제가 추가한 것은 두 가지입니다.
> 1. `subtitle`·`description` — P2의 "의미 1차, 도구명 2차" 위계를 데이터로 구현
> 2. **`metricLabels`** — 이게 핵심입니다. `metrics` 객체는 `{mapped_pct: 99.42, percent_duplication: 8.3, ...}` 형태로 오는데, 키 목록이 단계마다 다르고 앞으로 늘어납니다. 라벨 매핑을 레지스트리에 두고 **매핑 없는 키는 키 원문 + 값 그대로 표시**하면, 백엔드가 새 지표를 추가해도 화면이 자동으로 받아냅니다
>
> **금지 사항**: `if (stepId === '03_alignment')` 같은 분기. 이걸 한 번 허용하면 레지스트리가 무력화됩니다.

**향후 등록만 하면 되는 것** (지금은 만들지 않음)
`raw-qc` · `alignment-qc` · `gene-coverage` · `exon-coverage` · `variant-table` · `filtering` · `annotation` · `benchmark` · `acmg` · `interpretation` · `ai-explanation`

> **근거 — `isAvailable`이 핵심인 이유** `[코드근거]` + `[설계판단]`
>
> 현재 결과 화면은 데이터가 없어도 탭과 점선 박스를 그립니다. `"백엔드 결과 데이터 연동 대기 중"` 박스가 화면을 채웁니다. **이게 "허접해 보인다"의 실질적 원인 중 하나입니다** — 사용자는 "만들다 만 화면"으로 읽습니다.
>
> `isAvailable`이 false면 **섹션 자체가 존재하지 않습니다.** 빈 카드를 그리지 않습니다. precheck 결과 화면에는 coverage 섹션이 "데이터 없음" 상태로 있는 게 아니라 **아예 없습니다.**
>
> `[표준]` 이건 NN/g 휴리스틱 #8 "Aesthetic and minimalist design"과 일치합니다 — 관련 없거나 거의 필요 없는 정보는 관련 있는 정보의 상대적 가시성을 떨어뜨립니다.
>
> **`scope` 필드의 근거** `[코드근거]` — F3. `precheck`와 `full`은 같은 화면의 두 상태가 아니라 **다른 화면**입니다. precheck에는 coverage·variant 데이터가 물리적으로 존재하지 않습니다. 이걸 조건부 렌더링으로 처리하면 컴포넌트 안에 `if (resultType === 'precheck')`가 흩어집니다. 레지스트리 레벨에서 분리하는 편이 깔끔합니다.

## 4-4. Artifact Category Registry

```ts
type ArtifactCategoryDef = {

  label: string;
  kinds: string[];
  order: number;
};
```

| id | label | 포함 kind (예) |
|---|---|---|
| `vcf` | 변이 파일 | `raw_vcf` `gvcf` `filtered_vcf` `normalized_vcf` `annotated_vcf` + index |
| `alignment` | 정렬 파일 | `analysis_ready_bam` `aligned_bam` `markdup_bam` + index |

| `report` | 요약·기록 | `core_summary` `methods` `provenance` `final_validation` `manifest` `software_versions` |
| `other` | 그 외 | 미분류 kind 자동 수용 |

> **근거** `[코드근거]` — `main.sh`가 등록하는 artifact의 `kind` 값이 **40여 종**입니다. 필터 칩을 40개 만들 수는 없습니다.
>
> `[설계판단]` **5개로 묶은 기준은 "사용자가 무엇을 하려고 이 파일을 찾는가"입니다.**
> - `vcf` — 다음 분석에 쓰려고
> - `alignment` — IGV로 열어보려고
> - `qc` — 품질을 확인하려고
> - `report` — 방법을 기록하거나 공유하려고
>
> 파일 형식(`.gz`, `.txt`, `.html`)이나 생성 단계로 묶지 않았습니다. 사용자의 목적이 분류 기준이 되어야 합니다.
>
> **`other` fallback이 필수인 이유** — 백엔드가 새 kind를 추가하면 미분류가 되는데, 이때 파일이 **화면에서 사라지면 안 됩니다.** 분류를 못 해도 표시는 되어야 합니다.

## 4-5. Report는 별도 세계가 아니다 `[계약]`

```
                 파이프라인 structured outputs
                            │
                            ▼
                     Results model
                    (GET /results 응답)
                   ╱        │        ╲
                  ▼         ▼         ▼
           Web Results   Report    AI / RAG
```

**계약 3가지**
1. 보고서는 **새 데이터 모델을 만들지 않습니다.** `GET /results` 응답을 그대로 소비합니다
2. `ResultSectionDef`에 `printable?: boolean`과 `PrintComponent?`를 나중에 추가하는 것으로 보고서를 구성합니다
3. AI 설명 기능도 같은 모델을 근거로 씁니다

> **근거** `[설계판단]` — 이 계약이 없으면 보고서를 만들 때 십중팔구 이렇게 됩니다: 백엔드에 `/report` 엔드포인트를 새로 만들고, 전용 데이터 모델을 만들고, `ReportPage`를 따로 만듭니다. 그러면 **같은 지표가 두 곳에 존재하고 언젠가 값이 어긋납니다.**
>
> 특히 이 프로젝트는 결과가 **연구·교육 목적이라도 재현 가능해야 합니다.** 웹 화면의 평균 깊이와 보고서의 평균 깊이가 다르면 그 자체가 신뢰 문제입니다.
>
> `[제품관찰]` Galaxy의 History 개념이 이 방향의 참고가 됩니다 — 분석 이력이 별도 시스템이 아니라 같은 데이터 위에 얹힌 뷰입니다.

> **근거 (사이드바 대신 상단 네비)** `[설계판단]` — 최상위 목적지가 **2개**(실행 목록 / 새 분석)뿐입니다. 사이드바는 목적지가 5개 이상일 때 값을 합니다. 2개짜리 사이드바는 화면 폭만 먹습니다.
>
> **근거 (runMode 배지)** `[코드근거]` — F3. 기본 설정에서 실제 분석이 안 되는데 **현재 화면 어디에도 그 사실이 없습니다.** 사용자가 12GB를 올리고 5시간을 기다린 뒤에 "산출물이 없다"를 알게 되는 구조입니다. 상시 노출이 필요합니다.
>
> **근거 (푸터 면책 고정)** `[코드근거]` + `[표준]` — `core_summary.json`과 `provenance.json`이 `intended_use: "research and education only; not a diagnostic result"`를 기록하고, InterVar 요약은 `limitations` 3문장을 명시적으로 남깁니다. **파이프라인 자체가 이 경고를 모든 산출물에 넣고 있는데 화면만 빠뜨리면 안 됩니다.**
> InterVar 원 논문도 결과가 자동 근거 적용 단계이며 수동 검토가 필요하다고 명시합니다.
> 참고: Li Q, Wang K. Am J Hum Genet. 2017;100(2):267-280 (21장)

## 7-2. 간격 스케일 (4px 기준)

```
4  8  12  16  20  24  32  40  48  64
```

> **근거** `[디자인시스템]` + `[코드근거]`
>
> 4px 그리드는 대부분의 디자인 시스템(Carbon, Material 등)이 채택한 관례입니다. 8px 배수만 쓰면 배지 내부 여백 같은 작은 조정이 안 되고, 2px까지 열면 규칙이 무너집니다.
>
> `[코드근거]` **현재 코드에 임의값이 흩어져 있습니다** — `py-2.5`, `w-[260px]`, `w-[110px]`, `text-[11px]`, `left-[9px]`, `h-[calc(100%-8px)]`. 이런 값이 늘어나면 화면마다 리듬이 달라지고, 이게 "손으로 대충 맞춘 느낌"의 정체입니다.
>
> `[설계판단]` **10개로 제한한 것이 핵심입니다.** 값이 많으면 규칙이 없는 것과 같습니다.

## 7-3. 정렬 규칙

| 대상 | 규칙 |
|---|---|
| 좌측 기준선 | 헤더 로고 · 탭 · 섹션 제목 · 본문 · 테이블 첫 열이 **전부 같은 x** |
| 텍스트 | 항상 좌측. 가운데 정렬은 **빈 상태와 404에서만** |
| 숫자 | 테이블에서 **우측 정렬 + `tabular-nums`** |
| 단위 | 숫자에 붙이되 별도 span, 한 단계 밝은 색·작은 크기 |
| 지표 타일 | 같은 행의 큰 숫자는 **베이스라인 정렬** |
| 아이콘 | 16px 고정, `flex items-center gap-2` |
| 폼 입력 | 라벨 **위**, 컨트롤 아래 |
| 읽기 전용 요약 | 2열 정의형. **라벨 열 고정 180px** |
| 테이블 열 | 텍스트=좌 · 숫자=우 · 배지=좌 · 액션=우 |

> **근거 (숫자 우측 + tabular-nums)** `[표준]` + `[코드근거]`
>
> 표에서 숫자를 우측 정렬하면 자릿수가 세로로 정렬되어 **크기 비교가 시각적으로 가능해집니다.** 이건 회계·통계 표기의 오랜 관례입니다.
>
> `tabular-nums`(CSS `font-variant-numeric`)는 숫자 글리프 폭을 균일하게 만듭니다. **이 프로젝트에서는 필수입니다** — 3초마다 폴링으로 값이 바뀌는데(F5), 비례폭 숫자면 `99` → `100`에서 열 폭이 흔들려 화면이 떱니다.
>
> **근거 (폼 라벨을 위에 두는 것)** `[설계판단]` — 좌측 라벨은 영어 UI에서 흔하지만 **한국어는 라벨 길이 편차가 큽니다** (`참조 유전체` 5자 vs `최소 Genotype Quality (GQ)` 20자 이상). 좌측 라벨 열을 고정하면 짧은 라벨 옆이 크게 비고, 고정 안 하면 컨트롤 시작점이 제각각이 됩니다.
> **단, 읽기 전용 요약(KeyValueList)은 좌측 라벨입니다.** 조작하지 않고 스캔하는 화면에서는 라벨-값 쌍이 나란한 편이 읽기 쉽고, 라벨 열을 180px로 고정할 수 있습니다.
>
> **근거 (좌측 기준선 일치)** `[설계판단]` — 이게 **"사람이 만든 느낌"의 절반**입니다. AI가 만든 화면이 어색한 흔한 이유가, 섹션마다 컨테이너를 따로 잡아서 좌측 시작점이 미세하게 다른 것입니다. 눈에 띄지 않지만 전체적으로 정돈되지 않은 인상을 만듭니다.

> IBM Carbon은 tile 컴포넌트에 **과도한 그림자를 넣지 말라고 명시**합니다. 그림자는 "이 요소가 다른 레이어에 떠 있다"는 뜻이어야 하는데, 페이지 안에 나란히 놓인 카드는 떠 있지 않습니다.

>

> **근거 (반경 4/8 두 값)** `[코드근거]` — 현재 코드는 `rounded-xl`(12) `rounded-lg`(8) `rounded`(4) `rounded-full` `rounded-4xl`을 혼용하고, CSS의 `--radius`도 `:root`(0.625rem)와 `@theme`(0.5rem)에서 이중 정의되어 있습니다. **값이 많은 게 문제가 아니라 규칙이 없는 게 문제입니다.** 두 값으로 줄이고, "조작 요소는 4 / 담는 요소는 8"이라는 규칙을 붙였습니다.

# 8. 색상 시스템

## 8-1. 전략 — 색을 층으로 나눈다

| 층 | 역할 | 어디에 |
|---|---|---|
| 중립 | 구조 · 텍스트 · 경계 | 화면의 대부분 |
| 브랜드 | 사용자가 조작하는 것 | 화면당 primary는 하나 |
| 상태 | 시스템 상태 | 배지 · RunTape · 검증표 |
| 순차 | 크기 순서가 있는 데이터 | 커버리지 시각화 전용 |
| 범주 | 순서 없는 분류 | 향후 등록 모듈에서만 |

> **근거** `[설계판단]` + `[코드근거]`
>
> **문제의식**: "AI가 만들면 색이 2가지뿐이라 단조롭다"는 지적을 받았습니다. 흔한 해결은 색을 더 넣는 것인데, 그러면 지저분해집니다.
>
> **제 진단은 다릅니다.** AI가 만든 화면이 단조로운 이유는 색이 적어서가 아니라 **색을 쓸 근거가 없어서**입니다. 근거가 없으니 브랜드색 1개와 회색만 안전하게 쓰게 됩니다.
>
> 이 프로젝트에는 색을 쓸 근거가 이미 많습니다.

### 20× 기준에 대한 서술 규칙

화면 문구:
> **20× 미만을 저커버리지 표시 기준으로 사용합니다. 이 값은 본 파이프라인의 보고 기준이며, 임상 판정 기준이 아닙니다.**

> **근거** `[코드근거]` + `[설계판단]`
>
> `main.sh`의 `low_coverage_depth` 기본값이 `20`입니다. 즉 **이 프로젝트가 20×를 저커버리지 경계로 쓰는 것은 사실**입니다.
>
> 문제는 이걸 어떻게 설명하느냐입니다. v1에서는 "임상적으로 흔히 쓰는 기준선"이라고 썼는데, GPT 검토에서 지적을 받아 고쳤습니다.
>
> **고친 이유** `[설계판단]`:
> 1. 이 프로젝트는 연구·교육 목적(RUO)이고, 산출물마다 `intended_use`로 그걸 명시합니다
> 2. `[코드근거]` `coverage_min_mean_depth` 기본값이 `0`이라 **파이프라인 자체에 합격/불합격 판정 기준이 없습니다.** 임계값 판정을 하지 않는 파이프라인의 UI가 임상 기준을 암시하면 안 됩니다
> 3. 임상 검사실의 커버리지 기준은 검사실·패널·인증기관에 따라 다릅니다. 웹 화면이 특정 숫자를 "임상 기준"으로 제시하는 것은 과한 주장입니다
>
> **이 항목이 면접에서 좋은 소재입니다** — 도메인 지식이 부족한 상태에서 표현을 강하게 썼다가, 검토를 받고 주장 수위를 낮춘 사례입니다. 바이오 도메인에서는 이런 절제가 실제로 중요합니다.

> [YYYY-MM-DD HH:MM:SS] [ERROR] 메시지
> [ts] START {step_id} / [ts] DONE {step_id} status=… exit=… (Ns)
> ```

>
> 어두운 배경에서의 대비도 SC 1.4.3을 만족하도록 잡았습니다 (`#C9D4DE` on `#0B1116` ≈ 11:1).

## 8-9. 다크 모드 — v1 제외

> **근거** `[코드근거]` + `[설계판단]`

## 9-1. 서체 — IBM Plex 슈퍼패밀리

| 역할 | 서체 |
|---|---|
| UI · 본문 | **IBM Plex Sans KR** |
| 라벨 · 표 헤더 · 축 | **IBM Plex Sans Condensed** (대문자 + 자간 확장) |
| 데이터 · ID · 로그 · 해시 | **IBM Plex Mono** |

> **근거 (한국어가 결정적이었습니다)** `[코드근거]` + `[설계판단]`
>
> 현재 코드는 `@fontsource-variable/geist`를 로드하고 `html { @apply font-sans }`로 적용하는데, **Geist에는 한글 글리프가 없습니다.** 즉 UI 텍스트의 거의 전부인 한글은 시스템 폰트로 폴백됩니다. 결과적으로 **라틴 문자와 한글이 다른 서체로 렌더링됩니다** — 숫자·영문 지표명과 한국어 라벨이 한 줄에 섞이는 이 화면에서는 눈에 띄는 문제입니다.
>
> IBM Plex는 **Sans KR이 공식 제공되어 라틴과 한글이 같은 설계 언어를 공유합니다.** 이게 다른 후보(Inter, Geist, Public Sans)와의 결정적 차이입니다.
>
> **부가 이유**:
> - Plex Mono는 자릿수 구분(0의 슬래시, 1의 세리프)이 명확해 SHA-256·경로·로그에 적합합니다
> - Plex Sans는 IBM의 엔지니어링 제품 계열에서 나온 서체라 계측 도구의 인상과 맞습니다
> - Sans / Condensed / Mono가 한 슈퍼패밀리라 **어울림이 보장되고, 로딩할 패밀리 수가 늘지 않습니다**
>
> **Condensed를 세 번째 역할로 쓴 것** `[설계판단]` — 별도 서체를 추가하지 않고 역할을 하나 더 만드는 방법입니다. 대문자 + 자간 확장한 Condensed는 **계측 장비 패널의 라벨 인상**을 주고, 실용적으로도 좁은 테이블 열에서 유리합니다. 주제와 기능이 동시에 맞는 선택입니다.

>
> **근거 (한국어 행간 1.55)** `[설계판단]` — 한글은 라틴보다 글자 밀도가 높아 같은 행간에서 더 빽빽해 보입니다. 영문 UI의 관례적 1.4~1.5보다 약간 넉넉하게 잡았습니다.

## 11-2. 셀 폭은 균등 고정 — v1 판단을 뒤집은 부분

> **v1에서 제안했던 것**: 완료 단계의 셀 폭을 `elapsedSeconds`에 비례시켜, 한 요소가 상태·시간·내비게이션 3가지를 동시에 표현한다.
>
> **철회한 이유** `[설계판단]` — GPT 검토에서 지적받았고, 검토해보니 맞았습니다.
>
> | 문제 | 설명 |
> |---|---|
> | **클릭 대상이 움직인다** | 실행 중에는 현재 단계 폭이 매초 늘어납니다. 셀을 눌러 단계 상세로 가는 것이 이 컴포넌트의 주 기능인데, **조작 대상이 계속 이동합니다** |
> | **한 단계가 화면을 독점한다** | 정렬 90분 · 변이 검출 150분이면 나머지 6단계가 몇 픽셀로 눌립니다. 짧은 단계는 클릭도 안 됩니다 |
> | **접근성 위반** | 최소 폭이 보장되지 않으면 WCAG 2.2 SC 2.5.8 Target Size (Minimum, 24×24 CSS px)를 충족할 수 없습니다 |
>
> **제가 놓친 것**: 시각적 정보 밀도에 집중하다가 **조작 안정성**을 고려하지 않았습니다. 정보를 많이 담는 것과 쓰기 좋은 것은 다릅니다.

**수정 규격**

| 항목 | 규칙 | 근거 |
|---|---|---|
| 셀 폭 | **모든 단계 균등.** 컨테이너를 `plannedSteps.length`로 등분 (최소 24px, 미달 시 가로 스크롤) | `[표준]` SC 2.5.8 |
| 셀 색 | 8-4 상태색 배경. 테두리 없음, 셀 간격 2px | `[설계판단]` 셀 간격이 곧 구분선 |
| 현재 단계 | 하단 4px 브랜드색 마커 + 은은한 스캔선 왕복(2.4초). reduced-motion이면 정적 마커만 | `[표준]` SC 2.3.3 / `prefers-reduced-motion` |
| optional 단계 | 셀 상단 2px 점선으로 core와 구분 | `[코드근거]` `STEP_KIND`의 core/optional 구분 |
| 소요 시간 | `lg`는 셀 아래 숫자, `md`/`sm`은 툴팁 | `[설계판단]` |

## 11-4. 왜 여전히 시그니처인가

| 근거 | 설명 |
|---|---|
| **주제에서 나왔다** `[제품관찰]` | 젤 레인 · 시퀀싱 레인 · 커버리지 트랙 — 이 도메인의 시각 언어가 가로 띠입니다. DNA 나선 일러스트 같은 장식 대신 **실제로 쓰는 표현**을 씁니다 |
| **밀도 문제를 푼다** `[설계판단]` | 세로 체크리스트 타임라인은 8~9단계에 400px 이상 필요합니다. 가로 띠는 32px에 들어가 목록 행과 헤더 양쪽에 쓸 수 있습니다 |
| **단계 수에 종속되지 않는다** `[코드근거]` | 균등 분할이라 1단계(precheck)든 12단계(향후)든 그대로 동작합니다. P0 원칙과 일치합니다 |
| **애니메이션은 이것 하나만** `[설계판단]` | 진행률 바 트랜지션(200ms)과 드로어 슬라이드(160ms)를 제외하면 다른 모션이 없습니다. **한 곳에 몰아넣으면 그게 기억에 남고, 흩뿌리면 산만해집니다** |

> **디자인 관점의 정직한 평가** `[설계판단]`
>
> 시간 비례 폭을 뺀 뒤로 Run Tape의 독창성은 v1보다 줄었습니다. 남은 것은 "가로 띠 + 스캔선 + 3가지 크기 재사용"입니다.
>
> **그래도 유지한 이유**: 세로 타임라인이었다면 목록 행에 넣을 수 없었고, 실행 목록에서 8건의 진행 상태를 한눈에 비교할 수 없었습니다. **독창성이 줄어도 기능이 남으면 유지합니다.** 반대였다면 버렸을 것입니다.

# 13. 상태 · 에러 · 빈 화면

## 13-1. 모든 화면이 가져야 할 4가지 상태

| 상태 | 처리 |
|---|---|
| **로딩** | 스켈레톤. 스피너는 인라인 버튼에서만. 실제 크기와 동일하게 |
| **정상** | — |
| **비어 있음** | 상태 설명이 아니라 **다음 행동 제안** |
| **오류** | 원인 + 해결 방법 + 재시도 경로 |

> **근거** `[설계판단]` + `[표준]`
>
> **이 4가지를 전부 정의하는 것이 "디자이너가 만든 화면"과 "AI가 만든 화면"의 가장 큰 차이입니다.** AI는 대개 정상 상태만 만듭니다. 그래서 실제로 써보면 로딩 중에 화면이 튀고, 데이터가 없으면 빈 박스가 남고, 실패하면 아무 일도 안 일어납니다.
>
> `[표준]` 스켈레톤을 실제 크기로 그리는 것은 레이아웃 이동(CLS)을 막기 위해서입니다. 폴링으로 데이터가 들어올 때마다 화면이 튀면 조작이 어려워집니다.
>
> `[설계판단]` **빈 화면을 "다음 행동"으로 쓰는 것**이 핵심입니다. `데이터가 없습니다`는 상태 보고이고, `아직 실행한 분석이 없습니다 + [첫 분석 시작]`은 안내입니다. 빈 화면은 사용자가 막힌 지점이고, 막힌 곳에 출구를 놓는 게 UI의 일입니다.

## 13-2. 폴링 상태 표시

| 조건 | 헤더 표기 |
|---|---|
| 정상 | `3초 전 갱신` |

## 13-4. `manifestConsistent` — 검토 의견을 반려한 사례

> **받은 지적** `[GPT 검토]` — "`manifestConsistent: false`는 산출물 manifest와 실제 상태 사이에 문제가 있다는 뜻이므로 warning으로 드러내야 한다. 원칙은 `정상값 → 조용히 숨김 / 이상값 → 적극 노출`이다."
>
> **원칙에는 동의합니다.** P9로 채택했습니다. **다만 이 필드에는 적용하지 않습니다.**
>
> **반려 근거** `[코드근거]`
>
> `artifact_reader.py`의 주석이 명시합니다 — **`manifestConsistent: false`는 full 실행에서 정상값**입니다. 이유는 구조적입니다:
> ```
> 99_finalization이 artifact_manifest.json을 씁니다
>   → 그 시점에는 아직 finalization 자신의 산출물(methods.md, provenance.json,
>     core_summary.json, final_validation.tsv)이 등록되기 전입니다
>   → 따라서 manifest는 항상 artifacts/*.json의 합집합보다 짧습니다
>   → 즉 full 실행에서 이 값은 항상 false입니다
> ```
>
> `[설계판단]` **이걸 경고로 올리면 모든 정상 full 실행에서 경고가 뜹니다.** 경고가 늘 뜨면 사용자는 경고를 무시하게 되고, 진짜 경고까지 무시하게 됩니다. 경고 피로(alert fatigue)는 안전 문제입니다.
>
> **대신 이렇게 합니다.**
>
> | 필드 | 처리 | 근거 |
> |---|---|---|
> | `manifestPresent: false` | 재현성 탭에 사실로 표기 | 매니페스트가 아예 없는 건 비정상입니다 |
> | `manifestConsistent` | **재현성 탭에만 사실로 표기.** 사용자 경고 아님 | 위 |
> | **`suppressedCount > 0`** | **파일 탭 상단에 경고** | `[코드근거]` 형식 오류나 경로 이탈(path traversal)로 제외된 항목 수입니다. 이건 진짜 이상 신호입니다 |
>
> **`suppressedCount`가 지적이 찾던 신호에 더 정확히 대응합니다.**
>
> **면접에서의 활용** — 좋은 원칙을 받아들이되, 코드 사실과 대조해서 적용 대상을 조정하고, **더 나은 대체 신호를 제시한** 사례입니다. 원칙을 기계적으로 적용하지 않았다는 점이 요지입니다.

> **근거 (TanStack Query)** `[코드근거]` + `[설계판단]`

> - `refetchInterval: 3000` — 폴링이 한 줄
> - terminal 도달 시 `refetchInterval: false` — 자동 중단(13-2)
> - `refetchOnWindowFocus` — **5시간짜리 작업에서 창을 다시 열었을 때 즉시 최신 상태**를 봅니다. 직접 구현하면 꽤 번거롭습니다

> 2. shadcn 시맨틱 토큰 (`--background` `--primary`, oklch)
> 3. `@theme` 블록 (`--color-background` 등, hsl)
>
> 게다가 `@theme inline`이 `--color-*`를 다시 2번 토큰으로 재매핑합니다. `--radius`는 `0.625rem`과 `0.5rem`으로 이중 정의됩니다. **어느 값이 최종 적용되는지 코드만으로 판단하기 어렵습니다.**
> 이게 "색이 일관되지 않은 느낌"의 구조적 원인입니다. 새 프로젝트에서는 `styles/tokens.css` **하나만** 둡니다.

# 22. 부록 — 면접 예상 질문과 답변

> 포트폴리오 발표를 전제로 정리했습니다. **답변은 외우는 대본이 아니라 논지의 뼈대입니다.**

### Q1. 이 프로젝트에서 본인이 한 일을 한 문장으로 설명해 주세요.

> 이미 완성된 백엔드가 만들어내는 데이터가 화면에 하나도 연결돼 있지 않은 상태였습니다. **코드를 전수 조사해서 백엔드가 실제로 줄 수 있는 것과 줄 수 없는 것을 확정하고, 그 위에서 정보구조와 화면을 다시 설계했습니다.**
>
> 근거로 쓸 수치: 백엔드 API 13개 중 결과 관련 4개가 호출 0건. 산출물 40여 종, 정량 지표 60여 개가 미노출.

### Q2. "허접해 보인다"는 문제를 어떻게 진단했나요?

> 색이나 폰트 문제로 보지 않았습니다. 원인을 5개 층으로 분해했고, **시각 시스템은 그중 하나**였습니다.
>
> 예를 들어 결과 화면이 막다른 길인 원인은 navigation state 의존이었고, 백엔드는 이미 `profileId`를 응답에 넣어주고 있었습니다. **디자인 문제가 아니라 데이터 흐름 문제**라 색을 아무리 바꿔도 화면은 비어 있습니다. (2장)

### Q3. 색 팔레트를 어떻게 정했나요? 왜 단조롭지 않다고 보나요?

> **색을 층으로 나누고 각 층에 역할을 하나씩만 줬습니다** — 중립 / 브랜드 / 상태 / 순차 / 범주.
>
> AI가 만든 화면이 단조로운 이유는 색이 적어서가 아니라 **색을 쓸 근거가 없어서**입니다. 이 프로젝트에는 근거가 이미 많았습니다 — 상태 6종, 커버리지 6구간, 검증 3종.
>
> 커버리지 램프는 viridis를 썼는데, 이건 취향이 아니라 **matplotlib 기본 컬러맵이자 생물정보학 그림의 사실상 표준**이라 대상 사용자에게 학습 비용이 0입니다. (8장)

### Q4. 접근성은 어디까지 고려했나요?

> WCAG 2.2 AA를 기준으로 잡았습니다. 상태색은 흰 배경 대비 6.4~8.2:1로 SC 1.4.3을 통과하고, 색만으로 상태를 전달하지 않도록 아이콘+텍스트+색 3중으로 만들었습니다(SC 1.4.1).
>
> **한 가지 정정한 항목이 있습니다.** 처음에는 터치 타깃을 44×44로 잡았는데, 44×44는 SC 2.5.5 Target Size (Enhanced)로 **Level AAA**입니다. WCAG 2.2에서 새로 추가된 AA 기준은 SC 2.5.8로 **24×24 CSS px**입니다. 검증 과정에서 확인하고 고쳤습니다. (14장)

### Q5. 확장성을 고려했다고 했는데, 어떻게 검증하나요?

> "확장 가능하게 설계했다"는 검증할 수 없는 주장이라, **검증 가능한 명제로 바꿨습니다.**
>
> - 백엔드가 `12_gene_coverage` 단계를 추가하면 → 고칠 파일 **1개** (Step Registry)
> - 결과에 benchmark 섹션이 추가되면 → **2개** (ResultSection Registry + 섹션 컴포넌트). 기존 페이지 무수정
> - `GET /api/jobs`가 생기면 → **2개**. 화면 무수정
>
> 레지스트리 3종(Step / ResultSection / ArtifactCategory)이 이걸 가능하게 합니다. (4장, 16-3)

### Q6. 설계하면서 판단을 바꾼 적이 있나요?

> 세 번 있습니다. 가장 큰 건 **Run Tape의 셀 폭**입니다.
>
> 처음에는 완료 단계의 폭을 실제 소요 시간에 비례시켜서 "한 요소가 상태·시간·내비게이션 3가지를 표현한다"고 설계했습니다. 검토에서 지적을 받고 보니 **실행 중에는 현재 단계 폭이 매초 늘어나서 클릭 대상이 계속 움직입니다.** 이 컴포넌트의 주 기능이 단계 상세로 가는 내비게이션인데, 조작 대상이 불안정해집니다. 게다가 최소 폭이 보장되지 않아 SC 2.5.8도 위반합니다.
>
> **시각적 정보 밀도에 집중하다가 조작 안정성을 놓친 것**이었습니다. 균등 폭으로 고정하고, 시간 비교는 완료 후에만 렌더링되는 별도 막대 차트로 분리했습니다. (11-2)

### Q7. 검토 의견을 반려한 적도 있나요?

> 하나 있습니다. `manifestConsistent: false`를 경고로 노출하라는 의견이었습니다. 원칙("정상값은 조용히, 이상값은 크게")에는 동의해서 설계 원칙 P9로 채택했습니다.
>
> 그런데 **코드를 확인하니 이 필드는 full 실행에서 항상 false입니다.** finalization 단계가 자기 자신의 산출물을 등록하기 전에 manifest를 쓰기 때문에 구조적으로 불일치합니다. 경고로 올리면 모든 정상 실행에서 경고가 떠서 경고 피로를 만듭니다.
>
> 대신 **`suppressedCount > 0`을 경고로 올렸습니다.** 형식 오류나 경로 이탈로 제외된 항목 수라, 지적이 찾던 신호에 더 정확히 대응합니다. (13-4)

### Q8. AI로 만든 UI를 다시 설계한 거면, 이번에도 AI를 쓸 텐데 뭐가 다른가요?

> **AI에게 맡긴 것 자체가 문제가 아니라 제약을 안 준 것이 문제였습니다.**
>
> 처음에 빠졌던 것을 역산하면 네 가지입니다 — 데이터 제약, 디자인 토큰, 금지 목록, 상태 요구.
> - 데이터 제약이 없으니 존재하지 않는 결과 뷰 7종을 만들었습니다
> - 토큰이 없으니 팔레트가 3벌 공존합니다
> - 금지 목록이 없으니 카드·그림자·강조색이 화면마다 다릅니다
> - 상태 요구가 없으니 정상 상태만 있고 로딩·빈·오류가 없습니다
>
> 이번에는 화면 단위로 쪼개고 매번 이 네 가지를 함께 넘깁니다. 검수 체크리스트 13개도 만들었습니다. (19장)

### Q9. 바이오 도메인 지식이 부족한데 어떻게 설계했나요?

> **모르는 것을 아는 척하지 않는 쪽으로 설계했습니다.**
>
> 예를 들어 커버리지 20× 기준을 처음에는 "임상적으로 흔히 쓰는 기준선"이라고 썼습니다. 검토에서 지적을 받았고, 확인해보니 이 파이프라인은 `coverage_min_mean_depth` 기본값이 0이라 **합격/불합격 판정 자체를 하지 않습니다.** 판정을 하지 않는 파이프라인의 UI가 임상 기준을 암시하면 안 됩니다.
>
> "20× 미만을 저커버리지 표시 기준으로 사용합니다. 이 값은 본 파이프라인의 보고 기준이며 임상 판정 기준이 아닙니다"로 고쳤습니다.
>
> **바이오 도메인에서는 주장 수위를 낮추는 것 자체가 실력**이라고 생각합니다. 파이프라인이 모든 산출물에 `intended_use: research and education only`를 기록하는 이유도 같습니다. (8-5)

### Q10. 이 설계의 약점은 무엇인가요?

> 세 가지를 말씀드릴 수 있습니다.
>
> **첫째, full 결과 화면이 실제 데이터로 검증되지 않았습니다.** full WES가 아직 한 번도 성공한 적이 없어서(실행 기록 6건 전부 check-only 실패), 결과 화면의 모든 수치가 mock입니다. 그래서 문서와 코드 양쪽에 mock 표기 규칙을 강제했습니다. 실제 실행 후 레이아웃이 바뀔 가능성이 있습니다.
>
> **둘째, 실행 목록이 브라우저 로컬 저장에 의존합니다.** 목록 API가 없어서인데, 다른 기기에서 조회할 수 없습니다. 백엔드 요청 1순위로 올렸고, 데이터 소스를 한 파일로 격리해서 교체 비용을 낮췄습니다.
>
> **셋째, 레지스트리 구조는 화면이 5개인 지금 시점에서는 과설계일 수 있습니다.** 로드맵에 보고서·벤치마크가 있어서 채택했지만, 그게 없다면 불필요한 추상화 계층입니다. **비용을 정직하게 인식하고 선택했다**는 점을 말씀드립니다.

# 23. 설명 계층(Explanation Layer) — 현재 관찰과 검토 방향

> **이 장은 확정 architecture가 아닙니다.** v3 작성 이후 실제 full WES 실행
> (`wes-20260904-201711-97ea7b`)과 Run Detail 구현을 거치며 드러난 **현재 관찰**과,
> 그에 대한 **검토 방향**을 기록한 것입니다. 아래 내용은 검증 결과에 따라
> 바뀔 수 있으며, 바뀌더라도 이 문서의 1~22장과 모순되지 않습니다.
>
> 3장 P2("시스템이 아니라 사람의 언어로 쓴다") · P5(점진적 공개) ·
> P10("예시 숫자를 사실처럼 만들지 않는다")의 연장선입니다.

## 23-1. 현재 관찰 `[코드근거]`

실제 Run과 구현을 조사해 확인한 사실입니다.

**초보자용 설명이 존재하고, 전부 고정 문구입니다.**
Run Detail은 단계별 설명(`registries/steps.ts`의 `purpose`)과 진단별 설명
(`registries/diagnostics.ts`의 `title`/`meaning`)을 보여줍니다. 이 문장들은
frontend 상수이며, runtime에 생성되는 문장은 없습니다.

**Run facts는 이미 상당히 구조화되어 있습니다.**
한 단계에서 validation 항목 4~11건, metrics 6~17종이 옵니다. 예를 들어
`05_coverage_qc`는 평균 깊이·0× 비율·저커버리지 비율·깊이별 누적 비율 6단계를
모두 구조화된 값으로 제공합니다.

**그런데 고정 설명이 그 수치를 충분히 쓰지 않는 경우가 있습니다.**
실제 Run에 `uncovered_bases_pct = 5.5761`이 있는데도, 단계 목록의 진단 설명은
"read가 전혀 관찰되지 않은 target 구간이 있습니다"라는 고정 문장입니다.
수치는 결과 탭의 커버리지 절까지 가야 보입니다.

**진단 코드의 발생 조건이 심각도를 구분하지 않는 경우가 있습니다.**
`UNCOVERED_TARGETS`는 비율이 0보다 크기만 하면 발생합니다. 0.001%와 60%가
같은 코드, 같은 고정 문장을 받습니다.

**일부 진단 코드는 이 프로젝트의 내부 코드입니다.**
`NM_MD_REPAIRED`는 SAM/BAM 표준의 상태명이 아니라 파이프라인이 정의한 이름입니다.
반면 `NM`·`MD`는 SAM 표준 optional tag이고 `INVALID_TAG_NM`은 Picard
ValidateSamFile의 실제 오류 타입명입니다. **재료는 표준이지만 조합된 코드는
우리 것**이라, 그대로 노출하면 표준 용어처럼 읽힐 수 있습니다.

## 23-2. 현재 검토 방향 `[설계판단]`

아래는 현재 기울어 있는 방향이며, 23-3의 검증 결과에 따라 조정합니다.

**primary execution status는 단순하게 유지합니다.**
사용자가 알아야 할 큰 상태는 `분석 대기 / 분석 중 / 완료 / 실패 / 취소됨`
정도입니다. 파이프라인이 `warning`으로 기록한 단계도 화면에서는 "완료"로 쓰고,
경고의 존재는 별도 층이 말하게 하는 방향을 검토하고 있습니다. 1-5의 상태 전수는
그대로 유효하며, 그중 무엇을 사용자 어휘로 노출할지의 문제입니다.

**세부 diagnostic은 의미를 먼저 전달합니다.**
`자동 복구 / 확인 필요 / 참고`처럼 색 없이도 읽히는 짧은 라벨을 앞에 두고,
코드는 전문가용 상세에 둡니다. 색은 보조 수단입니다(P7·14장).

**raw diagnostic code는 프로젝트 내부 코드임을 알 수 있게 합니다.**
표기 방식은 미정입니다 — 접두사, 라벨, 구분된 영역, tooltip 중 무엇이 나은지
실제 화면에서 판단합니다. 원칙만 정해 둡니다: **표준 생물정보학 용어와 내부
진단 코드가 같은 무게로 보이지 않게 한다.**

**설명을 세 층으로 나누어 검토하고 있습니다.**

| 층 | 성격 | 예 | 현재 판단 |
|---|---|---|---|
| 기본 설명 | Run이 달라져도 의미가 같음 | coverage/depth란 무엇인가 · BQSR의 목적 · dbSNP란 무엇인가 · NM/MD tag란 무엇인가 | 검증된 고정 설명으로 제공 가능 |
| 실제값 설명 | Run의 구조화 metrics를 써야 정확해짐 | 이번 Run에서 target의 몇 %가 0×였는지 · 실제 mean depth · 실제 variant count | LLM 없이 template + Run facts로 가능 |
| 복합 설명 | 여러 metrics·config·logs를 함께 봐야 의미가 섬 | coverage가 낮은 이유와 중요도 · 여러 warning의 종합 · 실패 원인과 다음 확인 단계 | 향후 RAG/LLM 활용 후보 |

현재는 **고정·template을 우선하고 필요한 복합 설명에만 AI를 보강**하는 쪽으로
기울어 있습니다. 이유는 재현성(같은 Run은 같은 화면), 3초 폴링 화면에서의 응답
속도, 그리고 없는 수치를 그럴듯하게 채우는 위험입니다. **다만 이것은 확정이
아니며**, 사용자가 실제로 어디에서 추가 설명을 원하는지는 써 보기 전에는
알 수 없습니다.

**실제 Run facts와 설명 콘텐츠를 분리합니다.**
4-2의 Step Registry가 이미 `description`을 예고했고, 실제 구현에서는 `purpose`로
들어갔습니다. 원칙은 그대로입니다 — **설명은 registry에, 수치는 API 응답에.**
컴포넌트 안에 문장이나 숫자를 직접 쓰지 않습니다(1-6·P10).

**같은 facts/knowledge를 보고서와 향후 AI에서 재사용할 가능성을 열어 둡니다.**
4-5가 "Report는 별도 세계가 아니다"라고 정한 것과 같은 이유입니다. 설명 지식이
UI 컴포넌트 안에 깊이 묻히면 보고서 생성기나 다른 소비자가 쓸 수 없습니다.
현재는 registry 파일에 모여 있어 이 조건을 만족합니다. **별도 knowledge 저장소로
분리할지는 두 번째 소비자가 생기는 시점에 판단합니다** — 지금 분리하면 이득 없이
파일만 늘어납니다.

## 23-3. 검증 방법

새 full Run을 **직접 사용하면서** 관찰합니다. 이미 끝난 Job을 열어 보는 것과
실행 중 화면을 따라가는 것은 다릅니다.

관찰할 질문:

- 어느 정보가 **고정 설명으로 충분**했는가
- 어느 정보에서 "그래서 이번엔 몇 %인데?"라고 **실제 수치를 바로 보고 싶어지는가**
- 어느 상황에서 "이게 왜 문제인지 더 설명해 줘"라고 **AI에게 묻고 싶어지는가**
- raw metric key가 실제 값과 함께 보일 때도 여전히 추상적인가 (4-2의 `metricLabels`)

> **전제하지 않을 것** `[설계판단]`
> 같은 입력이라도 새 Run에서 과거와 동일한 diagnostic이 발생한다고 가정하지
> 않습니다. 진단이 나오지 않으면 "진단 0건 화면"이 제대로 보이는지가 대신
> 검증 대상이 됩니다. 1-6의 mock 규칙과 같은 태도입니다.

## 23-4. 이 관찰 결과로 바뀔 수 있는 것

아래는 **지금 확정하지 않습니다.** 23-3의 결과에 따라 결정합니다.

- registry 구조 — `purpose`/`meaning` 외에 실제값 template을 넣을지, 넣는다면 형태
- knowledge storage — TS registry 유지 / 별도 파일 분리 / 그 시점
- RAG 도입 시점과 코퍼스 범위
- explanation routing — 코드가 결정할지, AI가 결정할지
- UI 정보 밀도 — 단계마다 설명을 항상 펼칠지, 접을지
- diagnostic severity를 파이프라인/백엔드 계약으로 올릴지, frontend에 둘지

> **왜 지금 확정하지 않는가** `[설계판단]`
> 이 문서가 판단을 세 번 뒤집은 기록을 가장 값진 부분으로 꼽는 것과 같은
> 이유입니다(0장·22장 Q6). 설명 계층은 **실제로 화면을 써 본 사람의 반응**이
> 가장 중요한 근거인데, 그 근거를 아직 확보하지 못했습니다. 근거 없이 확정한
> 구조는 나중에 뒤집기 어렵습니다.
